# Devlog — v0.1 : rendu de base (jalon M1)

Date : 2026-11 · Tag : `v0.1`

## Ce qui existe

Un lanceur qui affiche, avec SDL_GPU (Vulkan, D3D12 et Metal via SDL), une scène 3D dans une fenêtre :
un modèle glTF texturé en PBR (métal-rugosité, normal map, occlusion, émissif), un ciel et un éclairage
par image (IBL) calculés au chargement, un soleil directionnel avec ombres filtrées, un tonemapping
HDR → écran, des lignes de débogage, une interface Dear ImGui (F1) et une caméra libre. Les shaders
HLSL sont compilés hors ligne ; en Debug ils se rechargent à chaud. Le jeu, lui, n'appelle rien du GPU :
il ne voit que la table de services (ADR 0001).

Chiffres au moment du tag (Linux, mesurés, lignes de `.c .h .hlsl .py .sh .js`) : environ 13 000 lignes de
moteur (contre 3 600 à v0.0), 200 de jeu, 1 200 de lanceur, 20 400 de tests, 360 d'outils ; 52 entrées
CTest regroupant 658 cas de test (contre 18 et 143 à v0.0).

## Décisions marquantes

- Les shaders sont compilés hors ligne et chargés comme données ; la compilation à chaud n'existe qu'en
  Debug, avec repli sur le shader hors ligne (ADR 0004).
- Le jeu et le GPU sont séparés par un renderer à handles et à file de commandes (ADR 0005).
- Le PBR suit la spécification glTF (annexe B) ; l'écart à three.js est mesuré et expliqué plutôt que
  copié (`docs/pbr.md`).
- Le moteur observe ses propres appels de débogage par un enregistreur, parce que SDL ne permet pas de
  relire ce qui part vers le pilote (`docs/gpu-debug.md`).

## Ce que j'ai appris / ce qui a surpris

- **Une référence externe a ses propres écarts** : sur le casque, 60 – 85 % des pixels concordaient avec
  three.js ; après isolement de deux écarts de three.js à la spécification, 99,5 %. Sans cette mesure,
  on aurait « corrigé » le moteur vers une valeur moins exacte.
- **Un accord global peut cacher un désaccord local** : l'éclairage par image concorde à 3 – 4 % avec un
  ciel uniforme et diverge de 16 – 25 % avec un soleil 5 000 fois plus brillant que le ciel. Un test
  contre une référence CPU a permis de savoir de quel côté se trouve l'écart ; l'origine côté three.js reste
  une hypothèse.
- **Des tests qui ne voient rien ne testent rien** : les mutants de M1-19 ont montré que des appels SDL
  inobservables laissaient survivre des mutations ; il a fallu intercepter les appels à l'édition de liens
  (`--wrap`) pour les voir.
- **Les chiffres se mesurent sur la bonne machine** : tout mon environnement de test est du rendu logiciel ;
  aucun chiffre de performance n'a été produit hors de ta machine.

## Limites connues à la clôture

- Performance : aucune mesure sur GPU réel dans l'environnement de développement de l'assistant ; objectif
  60 FPS avec ombres à confirmer (section « Mesures sur RTX 5070 »).
- Windows, macOS, MSVC : non testés ; D3D12 demande `WinPixEventRuntime.dll` pour les groupes de débogage.
- RenderDoc lui-même n'a jamais été lancé sur le rendu : groupes et noms sont prouvés jusqu'au pilote.
- Ombres : un seul soleil, instables quand il tourne ; l'ombre n'affecte pas l'éclairage par image.
- glTF : un jeu d'UV, un sampler, pas d'`alphaMode`, pas d'extensions.
- Les shaders rechargés à chaud ne sont pas nommés dans les captures.
- Dette : 2 allocations inexpliquées dans la boucle de frame ; un SEGV NVIDIA sans cause établie ; des
  avertissements « dessin ignoré » à trier.
