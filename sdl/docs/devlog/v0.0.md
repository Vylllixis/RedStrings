# Devlog — v0.0 : fondations et outillage (jalon M0)

Date : 2026-11 · Tag : `v0.0`

## Ce qui existe

Un exécutable qui ouvre une fenêtre SDL3, lit clavier, souris et manette sous forme d'*actions*,
fait tourner la simulation à pas fixe de 60 Hz avec interpolation du rendu, lit un fichier de
configuration, et recharge le code du jeu à chaud sans perdre son état. Aucun rendu GPU : un carré
logiciel provisoire sert de témoin (le vrai rendu est M1).

Chiffres au moment du tag (Linux, mesurés) : environ 3 600 lignes de moteur, 200 de jeu, 250 de
lanceur, 2 750 de tests ; 18 entrées CTest regroupant 143 cas de test.

## Modules, dans l'ordre où ils ont été faits

| Domaine | Contenu |
|---|---|
| Build | CMake + presets (debug, relwithdebinfo, release, profile), dépendances figées, `-Werror`, ASan + UBSan en Debug, clang-format, clang-tidy, CI |
| Plateforme | fenêtre, événements, plein écran, vsync demandé avec repli, journal (console + fichier), assertions, horloge entière, boucle à pas fixe |
| Mémoire | 3 arènes (permanent, niveau, frame) avec poison ASan, tableau dynamique, pool à handles générationnels, hashmap à adressage ouvert, compteur d'allocations |
| Jeu | bibliothèque sans lien avec le moteur, table de services, rechargement à chaud (copie, attente de stabilité, vérification de version et de taille d'état) |
| Entrées | actions et axes, appuis verrouillés entre deux pas, zone morte radiale, clavier, souris, manette |
| Fichiers et config | chemins relatifs à l'exécutable, surveillance de fichier, `config.ini` (résolution, vsync, sensibilité, liaisons) |
| Outils | profileur Tracy optionnel, framework de tests |
| Docs | `architecture.md`, ADR 0001 à 0003, `profiling.md`, `conventions.md` |

## Décisions marquantes

- Le jeu ne lie pas le moteur ; une table de fonctions les relie (ADR 0001).
- Le code tiers suit des règles strictes, la dépendance C++ reste optionnelle (ADR 0002).
- « Zéro malloc » est vérifié par un compteur **et** par une règle lint (ADR 0003).
- L'horloge et la boucle fixe travaillent en entiers : pas de dérive cumulée.

## Ce que j'ai appris / ce qui a surpris

- **Tester ses tests** : casser volontairement le code (mutation) a révélé des tests qui passaient
  pour de mauvaises raisons (table de hachage saturée, doublon `bind.x`, ...). À refaire pour les
  modules à risque.
- **Un outil peut changer le comportement du système** : Tracy rend `dlclose` inopérant sous Linux,
  ce qui aurait fait recharger l'ancien code en silence. Détecté parce que le test du rechargement
  échouait uniquement avec Tracy.
- **« Zéro allocation » demande de définir ce qu'on compte** : SDL alloue paresseusement (il a
  fallu un échauffement), et l'affichage logiciel alloue 2 fois par image. La portée exacte est
  écrite dans l'ADR 0003.
- Un `memcmp` sur une structure contient des octets de remplissage : clang-tidy le signale, on
  compare champ par champ.

## Limites connues à la clôture

- MSVC et Windows : build et CI à confirmer ; aucun test local.
- Aucun test avec une vraie fenêtre, un vrai vsync, une vraie manette pendant le développement
  (environnement sans écran) : à faire à la main, voir la revue.
- Le rechargement à chaud ne détecte pas un réordonnancement de champs à taille égale.
- Les structures génériques (pool, map, array) ne sont pas encore utilisables depuis le jeu
  (`architecture.md`, §9).
- La configuration n'est pas rechargée à chaud.
